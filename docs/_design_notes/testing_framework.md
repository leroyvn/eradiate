# Eradiate testing framework design notes

## Requirements

1. The framework is based on pytest.
2. A statistical testing interface allows running various types of multidimensional hypothesis tests (*e.g.* z-test, chi-square, t-test)
3. Regression tests are managed with a third-party or home-grown pytest plugin that allows easily referencing and updating references against which results are compared.
4. The implementation of tests can be used for performance metering. Benchmark results can be output to JSON. The responsibility of tracking performance results from one version of the code to another is offloaded to the user, who has to save the JSON report manually.
5. Regression tests can be exported to a documented, executed notebook suitable for inclusion in a sphinx-based HTML documentation.
6. A test report can be exported as an HTML document with two selectable styles (either print-ready display or collapsible interactive display).
7. The print-ready HTML test report can be exported to PDF with a Python-based solution.
8. Plotting instructions in tests are skipped by default to accelerate execution.

## Design ideas

- **Req. 2**
  - Take inspiration from what is done with Mitsuba 3.
  - Consider making an interface to run multiple tests in a sequence, looping over one or several dimensions of the tested data tensor.
- **Req. 3**
  - Consider using pytest-regressions with a series of custom adapters for NumPy and xarray data comparison, with statistical testing and optional plotted output (e.g. in HTML report, see req. 6).
  - If pytest-regressions doesn't do the job, we'll have to go with a home-grown solution.
- **Req. 4**
  - Consider using pytest-benchmark for this. Check if benchmark results can be exported to JSON.
- **Req. 5**
  - Consider using jupytext for sync: does it fulfill all our requirements?
  - Find a way to hide cells from output. Choose well the rendering engine (nbsphinx or MyST-NB).
  - If jupytext doesn't do what we want, explore a custom solution.
- **Req. 6**
  - Consider pytest-html, check if CSS can be customized and whether images are allowed in the output.
- **Req. 7**
  - Consider Weasyprint.
- **Req. 8**
  - Consider pytest-plt. This plugin is limited, better to rip off the implementation and extend it how we need.

## Overview

This document specifies a pytest-based testing framework for Eradiate covering
statistical testing, regression testing with reference management, performance
benchmarking, notebook-based documentation of tests, HTML/PDF reporting, and
conditional plot generation. It is intended as a starting point for
implementation in a Claude Code session.

## 1. Foundation: pytest

All test code lives under `tests/`. The framework uses pytest as its sole test
runner.  Configuration goes into `pyproject.toml` under `[tool.pytest.ini_options]`.

## 2. Statistical testing interface

### Goal

Provide a reusable interface for running hypothesis tests (z-test, χ², t-test,
etc.) on multidimensional simulation output.  This replaces the current
`eradiate.test_tools.regression` module, which bundles statistical comparison
and reference data management into a single API (classes `Chi2Test`, `ZTest`,
`IndependentStudentTTest`, `PairedStudentTTest`, `SidakTTest`).

### Key differences from the existing module and from Mitsuba 3

The existing Eradiate test classes and Mitsuba 3's `mitsuba.chi2` module each
have design assumptions that don't carry over cleanly:

- **Mitsuba 3** drives sampling itself: its `ChiSquareTest` takes a
  `sample_func` and a `pdf_func`, draws samples, bins them, and runs the
  χ² test in a single call.  In Eradiate, **sampling is upstream**: the
  Monte Carlo simulation has already been run before the test is invoked,
  and the test receives pre-computed result arrays (typically xarray
  DataArrays or NumPy arrays) together with a reference.

- **The existing Eradiate module** (`eradiate.test_tools.regression`) bakes
  regression reference management into the statistical test classes
  themselves: each test knows how to locate, load, and update its own
  reference files.  In the new framework, **reference management is
  handled independently** by the regression fixture (§3, backed by
  pytest-regressions or a home-grown solution), and the statistical test
  classes are pure comparison functions — they take a result array and a
  reference array, and return a verdict.

This separation yields cleaner, more composable code: statistical tests can
be used outside the regression pipeline (e.g. in exploratory notebooks or
for ad hoc comparison against external reference data), and the regression
fixture can use either statistical or deterministic comparison depending on
context.

### Design

Create an `eradiate.testing.stats` module exposing:

- A `StatisticalTest` base class (or protocol) with a
  `run(result, reference, **kwargs) -> TestResult` method.  Both `result`
  and `reference` are NumPy arrays or xarray DataArrays provided by the
  caller — the test class never drives sampling or loads reference files.
  `TestResult` carries the test statistic, p-value, degrees of freedom,
  pass/fail outcome, and optional diagnostic data (histograms, density
  maps).
- Concrete implementations (preserving the existing test catalogue):
  - `ChiSquareTest`: goodness-of-fit test comparing a result histogram
    against a reference distribution on a discretised domain.
  - `ZTest`: element-wise z-test comparing a result array against a
    reference, with configurable significance level α.  Suitable for
    large-sample Monte Carlo outputs where the variance is known or
    estimated.
  - `IndependentStudentTTest`: two-sample t-test for comparing two
    independent result arrays.
  - `PairedStudentTTest`: paired t-test for element-wise comparison of
    matched result/reference pairs.
  - `SidakTTest`: t-test with Šidák correction for multiple comparisons.
- A `MultiTestRunner` helper that iterates over one or more dimensions of a
  data tensor (e.g. wavelength × viewing angle × surface type), runs the
  chosen test at each point, and aggregates results.  It applies a
  Bonferroni or Holm–Bonferroni correction to the family-wise significance
  level.
- A `_dump_tables()` / `_dump_plots()` method on each test class to emit
  diagnostic plots when the `--plots` flag is active (see §8).

### Integration with reporting

Each `StatisticalTest` subclass should be a first-class participant in the
reporting pipeline:

- When `--plots` is active, `_dump_plots()` saves diagnostic figures (observed
  vs. expected density, difference maps, histograms of residuals) via the
  `ert_plt` fixture (§8).
- When `--report` is also active, the saved figure paths are registered as
  report "extras" (via the `conftest.py` hook in §6), so that diagnostic
  plots appear inline in the HTML report next to the corresponding test.
- `TestResult` carries a `figures: list[Path]` attribute populated by the
  test's plotting methods.  The regression fixture (§3) and the report hook
  both consume this list.
- When both `--plots` and `--report` are off, no matplotlib import occurs
  and no figures are generated — the plotting code paths are fully
  short-circuited through the `PlotNull` mechanism (§8).

This means that a single invocation like
`pytest -m regression --plots --report=report.html` produces an HTML report
with every statistical test's diagnostics embedded, without any extra
scripting.

### Dependencies

`scipy.stats` for the underlying test implementations.  No dependency on
Mitsuba's own chi2 module (we want a self-contained Eradiate utility).

## 3. Regression testing

### Goal

Store reference data (NumPy arrays, xarray Datasets) alongside tests and
compare new runs against them, with configurable tolerances and a simple
regeneration workflow.

### Recommended approach: pytest-regressions + custom fixtures

**pytest-regressions** (MIT, v2.10+) provides `ndarrays_regression` and
`num_regression` fixtures that store references as `.npz` / `.csv` in a
`<test_module>/<test_name>/` data directory (via pytest-datadir).  Key features:

- Per-array and per-default tolerance via `default_tolerance=dict(atol=…, rtol=…)`
  and a `tolerances` dict keyed by array name.
- `--force-regen` flag regenerates all reference files in one run.
- Parametrised tests get separate reference files automatically.

**What we need to add** (as custom fixtures in `conftest.py` or a small
`eradiate.testing.regressions` module):

1. **`xarray_regression` fixture.**  Wraps an xarray Dataset/DataArray →
   converts to a dict of NumPy arrays (one per variable/coordinate) → delegates
   to `ndarrays_regression.check()`.  On regeneration, the inverse path stores
   the dict as `.npz`.  This avoids a NetCDF dependency in the test data
   directory and leverages the existing tolerance machinery.

2. **Statistical comparison mode.**  For Monte Carlo outputs where strict
   `atol`/`rtol` comparison is inappropriate, the fixture should optionally
   accept a `stat_test` argument (e.g. `stat_test="ztest"`) and delegate to
   the §2 statistical testing interface instead of `numpy.allclose`.  The
   fixture passes the result array and the stored reference array to the
   chosen `StatisticalTest.run()` method — it does not need to store
   variance or any additional metadata beyond what the test class requires,
   since reference files are plain arrays managed by the regression fixture,
   not by the test class itself.  This is the key architectural departure
   from the existing `eradiate.test_tools.regression` module, where each
   test class managed its own reference files.

3. **Optional plot attachment.**  When a regression test produces diagnostic
   plots (difference maps, histograms), these should be capturable by the
   HTML report (§6) and the notebook export (§5).

### Fallback

If pytest-regressions proves too rigid (e.g. its file naming doesn't
compose well with Eradiate's test layout), implement a minimal home-grown
`RegressionFixture` that:

- Stores references in a configurable directory (default:
  `tests/regression_data/`).
- Compares via `numpy.testing.assert_allclose` or the statistical interface.
- Supports `--force-regen` via a custom pytest option.
- Writes `.npz` for arrays, `.json` for metadata.

## 4. Performance benchmarking

### Tool: pytest-benchmark

pytest-benchmark (v5.2+) satisfies all requirements out of the box:

- The `benchmark` fixture wraps any callable and measures wall-clock time
  with automatic calibration (rounds, warmup).
- **JSON export**: `--benchmark-json=bench.json` dumps all timing data.
  `--benchmark-autosave` stores runs in `.benchmarks/` for later comparison.
  `--benchmark-save=<name>` gives the run a human-readable label.
- **Comparison & regression detection**:
  `--benchmark-compare=0001` compares against a saved run.
  `--benchmark-compare-fail=min:5%` fails the suite on regression.
- `benchmark.extra_info` dict lets us attach Eradiate-specific metadata
  (scene description, variant, grid resolution) to the JSON output.

### Integration with Eradiate tests

- Benchmark tests live in `tests/benchmarks/` and are excluded from the
  default test run via a pytest marker: `@pytest.mark.benchmark`.
- A convenience pixi task `bench` runs
  `pytest -m benchmark --benchmark-autosave --benchmark-json=…`.
- The JSON report is committed to a `benchmarks/` directory (or stored as a
  CI artefact).  Tracking across versions is the user's responsibility, as
  specified in the requirements.

### Note on ASV

ASV (airspeed velocity) was considered but rejected: it is heavier, requires
its own environment management, and duplicates what pytest-benchmark already
provides for our use case.  If long-term historical tracking with a web
dashboard becomes desirable, ASV can be introduced later as a complement.

## 5. Notebook export of regression tests

### Goal

Each regression test should be exportable to a documented, executed Jupyter
notebook suitable for inclusion in the Sphinx HTML documentation.

### Recommended approach: jupytext + MyST-NB

1. **Authoring format**: write regression tests as Python scripts in the
   **percent format** (`# %%` cell markers).  This is the primary source,
   lives under version control, and is runnable with `pytest` directly
   (via `jupytext --check 'pytest {}'` or simply `pytest test_file.py`).

2. **Jupytext pairing**: configure `jupytext.toml` to pair
   `tests/notebooks/*.py` ↔ `docs/source/tests/*.ipynb`.
   On `jupytext --sync`, the `.ipynb` is regenerated from the `.py` source.

3. **Sphinx rendering**: use **MyST-NB** (`myst_nb` Sphinx extension) to
   include the `.ipynb` files in the documentation build.  MyST-NB is
   preferred over nbsphinx for several reasons:
   - It supports MyST Markdown directives inside notebook cells, giving
     richer cross-referencing and admonition support.
   - The "glue" mechanism allows embedding notebook outputs (figures, tables)
     into other documentation pages.
   - It offers `nb_execution_mode = "off"`, which reads outputs directly
     from pre-stored `.ipynb` files without attempting execution — essential
     for Read The Docs (see below).

4. **Hiding cells**: use cell metadata tags to control visibility in the
   rendered notebook:
   - `"tags": ["remove-cell"]` hides both input and output (useful for
     imports, boilerplate, pytest fixtures).
   - `"tags": ["remove-input"]` hides the code but shows the output (useful
     for plots that should appear without the plotting code).
   - `"tags": ["hide-input"]` makes the code collapsible (click to reveal).
   In the percent format, tags are set via cell metadata:
   `# %% tags=["remove-cell"]`.

5. **Execution and the Read The Docs constraint.**  Eradiate notebooks
   cannot be executed on Read The Docs: the environment lacks the required
   native libraries (Mitsuba, Dr.Jit) and the computational resources to
   run radiative transfer simulations.  The workflow must therefore be:

   - **Locally or in CI**: run the notebooks via a dedicated pixi task
     (e.g. `pixi run nb-execute`) that calls
     `jupytext --to ipynb --execute tests/notebooks/*.py` to produce
     `.ipynb` files *with outputs embedded*.
   - **Commit the `.ipynb` with outputs** to the repository (or store them
     as CI artefacts and inject them before the docs build).  The `.py`
     percent-format scripts (without outputs) remain the primary source
     under version control; the `.ipynb` files are derived artefacts.
     Consider using `.gitattributes` with `nbstripout` *disabled* for
     the `docs/source/tests/` path, or a dedicated branch/CI step.
   - **On Read The Docs**: set `nb_execution_mode = "off"` in `conf.py`.
     MyST-NB will read the pre-stored outputs from the `.ipynb` files
     directly, with no kernel invocation at all.
   - **Guard against stale outputs**: a CI check can compare the
     modification timestamps of `tests/notebooks/*.py` and
     `docs/source/tests/*.ipynb` (or use `jupytext --test`) and fail
     if the notebook outputs are older than the source script.

6. **Gallery (optional).**  MyST-NB does not natively support thumbnail
   galleries.  If a gallery view of test notebooks is desired, use
   **myst-sphinx-gallery** (v0.3+), a lightweight Sphinx extension
   designed to work alongside MyST-NB.  It generates gallery pages from
   existing notebook outputs (no re-execution), using the first figure in
   each notebook as the thumbnail by default (configurable via the
   `notebook_thumbnail_strategy` option or per-image `alt="gallery_thumbnail"`
   attributes).  Configuration in `conf.py`:
   ```python
   extensions = ["myst_nb", "myst_sphinx_gallery"]
   myst_sphinx_gallery_config = {
       "examples_dirs": ["../tests/notebooks"],
       "gallery_dirs": ["test_gallery"],
       "default_thumbnail_file": "_static/default_thumb.png",
   }
   ```
   Alternatively, the gallery can be built with a simple hand-written
   RST/MyST page using Sphinx's `.. grid::` directive (from
   sphinx-design) with explicit thumbnail images — this avoids an extra
   dependency at the cost of manual maintenance.

### Parameterising notebooks across use cases

A single notebook script may serve as a tutorial, a regression test, and a
benchmark.  These use cases differ in two main ways:

- **Sample count / runtime.**  Tutorials must run quickly on low-end
  hardware (e.g. a laptop during a workshop), so they may use a reduced
  sample count.  Regression tests use the full count needed for
  statistical validity.  Benchmarks may use yet another configuration
  optimised for timing stability.
- **Plotting.**  Tutorials always produce plots (they are part of the
  narrative).  Tests show plots only when `--plots` is active.  Benchmarks
  typically never plot.

Rather than duplicating notebooks, these differences should be controlled by
a single "mode" parameter readable at runtime.  The recommended mechanism:

1. **An environment variable `ERADIATE_TEST_MODE`** with values `tutorial`
   (default when running in Jupyter), `test`, or `benchmark`.  The
   `conftest.py` sets it before test collection based on the pytest marker
   or CLI option; the pixi tasks `nb-execute`, `test`, `bench` set it
   explicitly.

2. **A thin helper** in `eradiate.testing`:
   ```python
   import os

   class TestMode:
       @staticmethod
       def get() -> str:
           return os.environ.get("ERADIATE_TEST_MODE", "tutorial")

       @staticmethod
       def is_tutorial() -> bool:
           return TestMode.get() == "tutorial"

       @staticmethod
       def spp(*, tutorial: int = 256, test: int = 4096,
               benchmark: int = 4096) -> int:
           return {"tutorial": tutorial, "test": test,
                   "benchmark": benchmark}[TestMode.get()]
   ```

3. **Usage in a notebook / test script:**
   ```python
   # %% tags=["remove-cell"]
   from eradiate.testing import TestMode

   spp = TestMode.spp(tutorial=256, test=4096)
   show_plots = TestMode.is_tutorial()  # or --plots flag in test mode
   ```

   When `--plots` is active in test mode, the `ert_plt` fixture (§8)
   takes precedence over `show_plots` — the fixture's no-op/active
   mechanism already handles this.  In tutorial mode, plotting code runs
   unconditionally.

4. **Conditional cell execution.**  For cells that should only run in
   tutorial mode (e.g. interactive widgets, verbose explanations), use
   a guard:
   ```python
   # %%
   if TestMode.is_tutorial():
       # ... display interactive plot, rich explanation, etc.
   ```
   When running as a test, the cell body is skipped but the cell itself
   still executes (no error).  For cells that must be *completely* absent
   from test runs (e.g. heavy visualisation imports), use cell tags:
   `# %% tags=["tutorial-only"]` and filter them out with a small
   jupytext pre-processor or a `conftest.py` hook that strips tagged
   cells before pytest collection.

### Interactive editing workflow

The current workflow — editing a notebook in JupyterLab while
`sphinx-autobuild` watches for changes and rebuilds the docs live — must
remain possible.

With jupytext pairing, the workflow becomes:

1. **Open the `.py` script as a notebook in JupyterLab** via the jupytext
   extension (right-click → "Open as Notebook", or simply double-click if
   jupytext is configured as default).  JupyterLab treats the percent-format
   `.py` file as a notebook with full cell editing and execution.

2. **On save**, jupytext updates both the `.py` source and the paired
   `.ipynb` (with outputs embedded).  The `.ipynb` is what Sphinx/MyST-NB
   reads.

3. **`sphinx-autobuild`** watches the `docs/source/` tree.  When the
   `.ipynb` is updated by jupytext on save, autobuild triggers a
   rebuild.  With `nb_execution_mode = "off"`, MyST-NB reads the
   pre-stored outputs directly — no re-execution during the Sphinx build,
   so rebuilds are fast (typically a few seconds).

4. The browser auto-reloads, showing the updated rendered page.

This preserves the same edit → save → see cycle as the current workflow.
The only change is that the author edits a `.py` file opened as a notebook
(rather than a native `.ipynb`), and jupytext handles the sync
transparently.

**Caveats to document:**

- Disable JupyterLab's autosave (or set a long interval) when
  simultaneously editing the `.py` file in an external editor, to avoid
  sync conflicts.
- If the author prefers to edit the `.ipynb` directly (e.g. for rapid cell
  experimentation), that also works — jupytext syncs in both directions.
  Just ensure the `.py` file is committed, not the `.ipynb`.

### Alternative considered: nbsphinx

nbsphinx also supports pre-executed notebooks: with `nbsphinx_execute =
"never"` (or simply by committing notebooks with outputs already stored),
it will render pre-stored outputs without attempting re-execution, which
would satisfy the Read The Docs constraint equally well.  It also has
built-in `nbgallery` support for thumbnail galleries.

However, MyST-NB is preferred for the following reasons:

- MyST-NB uses MyST-Parser to convert Markdown directly to the docutils
  AST, giving native access to Sphinx roles and directives (cross-references,
  admonitions, figure captions, etc.) using MyST's `{directive}` syntax
  directly in Markdown cells.  nbsphinx uses pandoc, which does not
  understand Sphinx constructs; the current workaround — embedding raw reST
  cells — works but forces authors to mix two markup languages in the same
  notebook.  With MyST-NB, these raw reST cells can be replaced with
  ordinary Markdown cells using MyST syntax, keeping the entire notebook
  in a single language.
- MyST-NB's "glue" mechanism allows embedding notebook outputs (figures,
  tables) into other documentation pages.
- MyST-NB's `jupyter-cache` integration provides smarter incremental
  caching when execution *is* desired (e.g. for local development).
- nbsphinx's `nbgallery` directive has known issues when used with
  `nbsphinx_execute = "never"` (thumbnails may not render correctly in
  that mode), whereas myst-sphinx-gallery is explicitly designed to work
  from pre-existing images without execution.

## 6. HTML test report

### Goal

Export a test report as a self-contained HTML document with two selectable
display styles: (a) a print-ready layout, (b) a collapsible interactive layout.

### Recommended approach: pytest-reporter-html1

**pytest-reporter-html1** (v0.9+) is preferred over the older pytest-html for
this use case because:

- It is Jinja2-based, making deep template customisation straightforward.
- It supports self-contained reports (CSS + images inlined) or split reports.
- The `asset` filter handles base64-encoding of images (plots, difference
  maps) into the report.
- Template inheritance (`{% extends "html1/index.html" %}`) allows overriding
  individual blocks (header, style, footer) without forking the whole template.

### Implementation

1. Install `pytest-reporter` + `pytest-reporter-html1`.
2. Create two Jinja2 templates in `tests/report_templates/`:
   - `print.html`: inherits from `html1/index.html`, overrides the `style`
     block to add `@media print` rules (page breaks between test modules,
     no collapsible sections, fixed font sizes).
   - `interactive.html`: inherits from `html1/index.html`, adds JavaScript
     for collapsible test sections (details/summary elements or a small
     toggle script).
3. Select at run-time:
   ```
   pytest --template=tests/report_templates/interactive.html --report=report.html
   pytest --template=tests/report_templates/print.html --report=report_print.html
   ```
4. To embed plots from regression tests, use a `conftest.py` hook
   (`pytest_runtest_makereport`) that attaches figure paths as "extras" to
   the test report item.  The template's `asset` filter base64-encodes them.

### Alternative: pytest-html

pytest-html (v4+) also supports custom CSS (`--css=…`), embedded images via
`pytest_html.extras.image(…)`, and self-contained mode (`--self-contained-html`).
It is simpler but less flexible for the two-template requirement.  Keep it as
a fallback if pytest-reporter-html1 proves too heavy.

## 7. PDF export from HTML report

### Tool: WeasyPrint

WeasyPrint (v68+, BSD licence, Python 3.10+) converts HTML+CSS to PDF.
It supports `@page` rules, running headers/footers, page numbering, and
`@media print` stylesheets — everything needed to produce a polished
print-ready PDF from the HTML report.

### Integration

Add a small script or `Makefile` target:

```python
# scripts/report_to_pdf.py
from weasyprint import HTML
HTML("report_print.html").write_pdf("report.pdf")
```

The print-ready HTML template (§6) should include `@page` CSS rules for
margins, page size (A4), and page-break hints (`page-break-before: always`
on `<h2>` module headings).

### Note

WeasyPrint requires system libraries (Pango, HarfBuzz, etc.).  Document the
dependency in `docs/contributing.rst` and provide a `[test-report]` optional
dependency group in `pyproject.toml`.

## 8. Conditional plot generation

### Goal

Plotting instructions in tests are skipped by default to accelerate execution.
Plots are only generated when explicitly requested.

### Recommended approach: custom fixture inspired by pytest-plt

pytest-plt's approach is sound (a `plt` fixture that returns a `Mock` when
`--plots` is not passed, and real `matplotlib.pyplot` otherwise), but the
library itself is limited and lightly maintained.  We should implement our own
fixture with the following improvements:

1. **`--plots [DIR]` CLI option**: registered via `conftest.py`
   `pytest_addoption`.  When absent, all plotting calls are no-ops (the
   fixture returns a lightweight mock/null object).  When present, plots
   are saved to `DIR` (default: `plots/`).

2. **`ert_plt` fixture** (to avoid shadowing `matplotlib.pyplot`):
   - When active: wraps `matplotlib.pyplot`, auto-generates a filename
     from the test node ID, calls `savefig()` + `close()` on teardown.
   - When inactive: returns a `PlotNull` object whose methods are all
     no-ops.  This is cheaper than `unittest.mock.Mock` (no call recording).
   - Supports `ert_plt.saveas = "custom_name.pdf"` to override the
     filename.
   - Supports multiple figures per test via `ert_plt.figure("label")`.

3. **Integration with HTML report (§6)**: when `--plots` is active and
   `--report` is also active, the fixture registers each saved plot path
   as a report "extra" so it appears in the HTML report.

4. **Integration with regression tests (§3)**: the `xarray_regression`
   fixture can optionally accept an `ert_plt` instance to generate
   comparison plots (reference vs. actual, difference map).

### Marker alternative

For tests where the plotting code is substantial and interleaved with the
test logic (not just a few `plt.plot()` calls at the end), use a
`@pytest.mark.plotting` marker.  A `conftest.py` hook skips the marked
sections (or the entire test) when `--plots` is not passed.

## 11. Implementation order (suggested)

1. **Plotting fixture** (`ert_plt`, `--plots` option) — unblocks visual
   debugging immediately.
2. **Statistical testing module** (`eradiate.testing.stats`) — core
   infrastructure needed by regression tests.
3. **Regression fixtures** (`xarray_regression`, pytest-regressions
   integration) — requires §2 for the statistical comparison mode.
4. **Benchmarking setup** (pytest-benchmark markers, `Makefile` target) —
   independent of the above.
5. **Notebook export pipeline** (jupytext pairing, MyST-NB integration) —
   requires regression tests to exist.
6. **HTML report templates** (pytest-reporter-html1 + plot embedding) —
   requires §1 and §3 to have reportable content.
7. **PDF export** (WeasyPrint script) — last step, depends on §6.
